# hx — design spec

**Status:** approved design, pre-implementation
**Date:** 2026-08-21
**Author:** jimx + Claude
**Supersedes:** nothing

An agent-driven web application security assessment harness that uses **Burp Suite
Community Edition as an engine**. Built for a security consultancy: the priorities are
extensibility, defensible evidence, and never harming a client's estate.

---

## 1. Purpose

Burp Community lacks four things Professional has: Scanner, Collaborator, project files,
and report generation. This harness supplies what a consulting practice actually needs
from those, while keeping Burp itself as the HTTP engine — its proxy, TLS handling,
HTTP/2, request mutation primitives, scope model, and browser.

The agent (Claude Code) remains a general web-assessment operator. The harness gives it
durable state, a check corpus, and safety rails; it does not constrain what the agent can
reason about.

**Explicit non-goal:** replacing Burp's UI. Repeater, Intruder, Comparer and the message
editor are better than anything we would build. `hx` owns *assessment state*; Burp owns
*manual manipulation*. Both run against the same engine at the same time.

## 2. Verified constraints

Everything here was measured on Burp Suite Community Edition 2026.7.3.52685, not assumed.
These facts are load-bearing; if a future change contradicts one, re-measure first.

| Fact | Consequence |
|---|---|
| Community loads arbitrary Montoya extensions with no restriction | The extension is the integration point |
| MCP truncates history at `MAX_HISTORY_ITEM_LENGTH = 5000`; a 1.2 MB response reads as 1,208,207 bytes in-JVM vs 10,032 chars for the *entire* history over MCP | **The extension is the data plane. MCP is a control channel only.** |
| `siteMap().add(AuditIssue)` is a silent no-op on Community | Findings live in our store, never Burp's Issues tab |
| Pro-only Montoya calls return `null`, they do not throw | Null-check `scanner()` and `collaborator()` everywhere |
| No request-rate throttle at any level. `http().sendRequest` sustains **2,896 req/s** sequential (n=300, p50 0.27 ms) and 1,829 req/s at 8 threads — **but only when the server closes the connection.** Against a keep-alive server every call blocks a fixed **1,003 ms** (n=50, min 1002.5, max 1004.4) waiting for a FIN it has already stopped needing. That wait parallelises exactly (16 threads → 14.4 req/s), no config knob changes it, and the batch `sendRequests(` is ~1000× slower than a loop of single calls (300 requests in 110 s). | Throughput is a **hazard**, not a feature — throttle is ours to impose. But the second is *latency, not a limit*: it is Burp waiting on connection teardown, not pacing. Never benchmark a rate limiter against a keep-alive target, and expect ~1 req/s per thread against real hosts, which mostly keep connections alive. |
| `persistence().extensionData()` does not survive restart | The extension is stateless across restarts; config must be re-pushed |
| `persistence().preferences()` survives restart (1 MB blob verified) | Usable for extension-local config, not for engagement data |
| Burp's 183 issue definitions ship as JSON in the Community jar | Report vocabulary comes free; extract once, vendor the JSON |
| `registerHttpHandler`, `proxy().registerRequestHandler`, `sendRequests`, `createResponseVariationsAnalyzer`, `registerSuiteTab` all work | Traffic hook, enforcement point, batching, differential oracle, kill switch |
| `registerSessionHandlingAction` **registers** on Community | Registration is not invocation. **v1 does not depend on it.** |

**Licence.** Burp Community's EULA Addendum D clause 2.1 grants use "for Your internal
business purposes (which may include the provision of a bespoke consultancy service to
clients where You are acting in a business advisory capacity)". Consulting use is
explicitly permitted. Two constraints: `hx` must never bundle or redistribute Burp, and
published analysis of Community's documented functionality must be provided to
PortSwigger simultaneously and identically.

---

**On that 1,003 ms.** It was found by an integration test that could not pass: a rate
limiter that never tripped because a single bridge read loop physically cannot issue two
sends inside one second. The earlier "320 req/s" was not wrong — it was measured through a
lab target left at `BaseHTTPRequestHandler`'s default `protocol_version = "HTTP/1.0"`,
which closes after every response, with a request that carried `Connection: close`. Both
halves put Burp on the fast path, and the figure was bounded by the MCP transport rather
than by Burp. Neither measurement was a throttle; the discriminator is entirely **whether
the peer closes the connection**. Burp does not trust a `Connection: close` *header* — it
waits for the actual FIN, then gives up after a fixed second.

The consequence: against real hosts hx pays roughly a second per request per thread. A
production profile's single-digit req/s makes that nearly free; a crawl does not.

**Decision: v1 accepts it and sends exactly what it was asked to send.** hx does not add
`Connection: close` on the way out, even though that would take a request from ~1,003 ms to
~0.3 ms. Two reasons. Evidence has to be defensible — a report that says "we sent this
request" must mean it, and a header hx injected is a header the client did not see us
declare. And connection-reuse behaviour is occasionally the thing under test, so rewriting
it can mask the finding.

Throughput is therefore a **threading** problem, not a framing one, and the measurements say
that works: the wait parallelises exactly, so N concurrent sends cost one second in total
rather than N. Fan-out belongs to whichever plan first needs to crawl at speed; until then
one request per second per thread is the honest number, and the profile that matters most —
production — was never going to run faster than that anyway.

## 3. Architecture

```
┌─ BURP SUITE COMMUNITY (engine) ──────────────┐
│  hx-bridge extension (Java, thin, stable)    │
│    · proxy request handler   ENFORCEMENT     │
│    · send path               ENFORCEMENT     │
│    · scope · rate · method · dangerous-path  │
│    · credential redaction (pre-hash)         │
│    · traffic push                            │
│    · STOP button (suite tab)                 │
└───────────────┬──────────────────────────────┘
                │ unix socket, length-prefixed frames
┌───────────────┴──────────────────────────────┐
│  hx harness (Python, fat, iterated)          │
│    · checks          ← the extensibility     │
│    · orchestration     surface               │
│    · state: SQLite + blobs (per engagement)  │
│    · tool layer ──┬── MCP adapter (v1)       │
│                   └── embedded loop (v2)     │
│    · web app (FastAPI + Jinja + htmx)        │
└──────────────────────────────────────────────┘
```

**Split rule.** The extension owns anything that must see every byte or must not be
bypassable. Python owns anything that changes often. When in doubt, ask: *"if this were
wrong or absent, could a bad check or a wedged harness hurt the client?"* If yes, it goes
in the extension.

**Isolation unit is the engagement.** One directory, mode 0700, containing its own SQLite
database, its own `blobs/` tree, its own config, and its own socket. Nothing is shared
across engagements — not blobs, not sockets, not a database. Client A's bytes cannot reach
client B's report.

```
~/hx/engagements/<engagement-id>/
  config.yaml        scope, targets, identities, safety profile
  hx.db              SQLite
  blobs/ab/cd/<sha>  content-addressed, engagement-local
  exports/
```

## 4. The enforcement invariant

> **Every byte that leaves this machine crosses exactly one of two enforcement points,
> both inside the JVM: the proxy request handler, or the send path.**

State it, test it, and never add a third egress path. The send path is enforced by a
single method — the only call to Montoya's HTTP API in the extension, asserted by a
structural test — so a third path cannot appear by accident.

**Implementation status (amended 2026-08-24).** The send path shipped in Plan 3. The proxy
request handler ships in Plan 4, ahead of the crawler rather than with it — §9's first
source of attack surface is an operator browsing the target, which needs the handler and
nothing else. From Plan 4 the invariant covers both points.

**Both points apply the same rules, but not to the same traffic, and the difference is WHO
IS DRIVING rather than which point it is.**

- **Scope is absolute at both points, for all traffic.** It is the client's boundary and
  the one thing no caller may spend. Out of scope is dropped and the drop is recorded.
- **Method allowlist, dangerous-path denylist, rate limit and budget constrain an AGENT.**
  They apply to the send path in full, and to crawler traffic in full. They do **not**
  apply to traffic from the operator's own browser.

The reasoning, recorded because the first version of this section said otherwise: those
four rules exist so a bad check or a runaway loop cannot hurt the client. A human clicking
a form is a deliberate act by the person legally responsible for the engagement, and
applying the agent's rules to them makes the highest-quality source of attack surface
unusable — `method.allow` refuses their login POST, the rate limit throttles their
browsing, and the run budget ends their session mid-page. Enforcement that drives an
operator off the proxy buys nothing: they browse without hx and the traffic is not
recorded at all.

The two sources are told apart by **which proxy listener the request arrived on**, never
by anything in the traffic itself. A property of the connection cannot be forged by a
hostile page; a header can.

Any denial produces a `denial` row and a distinct error class. Denials are never silent.

**Capture never gates enforcement.** Scope is decided from the extension's own
authorisation snapshot before anything is recorded. A wedged harness, a full queue or a
dropped record changes what `hx` KNOWS, never what it ALLOWS. The converse — that a
recording failure must be visible rather than silent — is §5's `run.dropped_total`.

**Initial and terminal state is DENY-ALL.** On connect the extension refuses every send
with `not_configured` until it receives one `configure` frame and ACKs a `config_epoch`.
This closes the window after a 02:00 Burp restart where the extension is live but
unconfigured.

**The crawler's browser is the second egress path, and it is enforced, not observed.**
`proxy().registerRequestHandler` returns `drop()` for out-of-scope destinations. Third-party
page resources are handled by policy, not by exemption:

- Out-of-scope destinations are dropped, and the drop is recorded.
- Identity is **never** attached to an out-of-scope destination.
- If dropping breaks rendering badly enough to hurt coverage, the fix is an explicit
  `render_allow` list in the engagement config — recorded, scoped, and reviewable — not a
  blanket exemption.

**Redirects.** Not auto-followed. Each hop is a distinct issuance with its own scope
decision and its own `exchange` row. Identity is never carried across a host change.
Redirect chains are capped.

**Rate limiting, method allowlist, dangerous-path denylist, and per-run budgets all live
in the extension.** A looping check or a wedged Python cannot exceed them. Defaults on a
`production` profile are single-digit req/s and `GET/HEAD/OPTIONS` only. The dangerous-path
denylist ships with sensible defaults (`logout`, password change, delete, purge) and is
separate from scope — "in scope" and "safe to touch automatically" are different questions.

**Auto-halt on target distress.** Rolling per-host window — the last 50 requests or 60
seconds, whichever is shorter. Issuance stops on a 5xx rate above **20%**, p50 latency
above **5×** a baseline taken from that host's first 10 requests, or **5 consecutive**
connection errors. These are engagement-config defaults, not constants: §14 flags that they
need tuning against a real client app, and a threshold you cannot change mid-engagement is
one you will fight.

**Implementation status (amended 2026-08-23).** Not yet true. Plan 3 ships all three
thresholds as the literals above, fixed at construction (`new Distress(clock, 0.20, 5.0,
5)`), and `configure` has no key to carry them — an unrecognised key is a hard
`bad_config`, so there is no wire for them either. The sentence above is the intent and
the wire work belongs to whichever plan first needs it against a real client app. Recorded
here rather than left as an unmet promise, because a spec that disagrees with its
implementation stops being consulted.

Related, and shipped: `Limits` takes the rate and budget from the **first** authorisation
and does not re-arm from a later one. Monotonicity is right for the budget — a run must
not talk itself into a larger one — but an operator lowering `limit.rate_rps` mid-run
because the target is wobbling is asking for something always safe. Until re-arming
exists, a later `configure` naming a different rate **or budget** must be **refused**, not
silently ignored: the failure mode to avoid is an operator who believes they slowed the
run down and did not. (Amended again the same day — the first wording said "rate", which
was a word short. The budget is the half with the stronger argument: a run must not talk
itself into a larger one, and silence is the worst answer to an attempt.)

One distressed host aborts the **whole run** — `run.status = aborted` with a `stop_reason`
— not just that host. Distress on one host is often the first sign of something the whole
test is causing. Restarting after a human has looked is cheap; explaining why the run kept
going is not.

**Kill switch, three independent paths:** a `halt` frame; the STOP button in the harness's
Burp suite tab; a sentinel file the extension polls. Any one works when the others are
wedged. The frame and the sentinel file ship with the send path; the suite tab is its own
piece of work, and until it lands two of the three paths exist.

**An operator halt is durable.** It is recorded in the engagement store *and* written as a
sentinel file, so it survives the harness dying, Burp dying, or both. A reconnect does not
clear it: after any peer's `hello` the harness re-asserts `halt` **before** any `configure`.
This matters because a restart during an incident is exactly when someone has already hit
stop — and because a `configure` re-authorises *scope*, never *issuance*. Only `resume`
re-arms.

The sentinel file exists to work when the bridge does not: an operator can create it from a
shell when the socket is dead or the agent has stopped responding. **If it cannot be read —
permissions, a vanished directory, an I/O error — the extension treats that as halted.**
Unknown state is stop.

## 5. Data model

SQLite per engagement. At every open: `journal_mode=WAL`, `synchronous=NORMAL`,
`busy_timeout=5000`, `foreign_keys=ON` (off by default per connection — none of the
declared relationships are enforced without it). **Exactly one writer connection**, fed by
an in-process queue; the web app reads on separate connections.

```sql
engagement(id, name, client, created_us, status, config_path)

-- Append-only. Never UPDATE. The one query that matters under dispute is
-- "what was in scope when request X was issued", and it must be answerable.
scope_version(id, engagement_id, yaml, sha256, effective_from_us, author, reason)
authorization(id, engagement_id, doc_blob, doc_sha256, signatory,
              valid_from_us, valid_to_us, scope_sha256)

run(id, engagement_id, kind, safety_profile, scope_version_id,
    started_us, ended_us, status, stop_reason, heartbeat_us,
    requests_issued, dropped_total)
    -- status: running | completed | aborted | killed | error
    -- kind:   browse | crawl | manual | scan        (amended 2026-08-24)
    -- an aborted run must never render as a clean one, and neither must one that
    -- merely STOPPED BEING UPDATED: a run left `running` with a stale heartbeat_us
    -- is a run whose harness died, and it resolves to `error`, not `completed`.
    -- dropped_total is the count of exchanges the extension could not hand over
    -- (§4's bounded queue). A run with drops has coverage numbers that are a
    -- FLOOR, not a count, and every report derived from it must say so.

-- Identity is the TEMPLATE, not the concrete URL. /order/1..9999 is one surface.
surface(id, engagement_id, method, scheme, host, port, path_template, query_key_set,
        kind, normaliser_version, first_seen_run, last_seen_run, exemplar_exchange_id,
        UNIQUE(engagement_id, method, scheme, host, port, path_template, query_key_set))
        -- kind: idempotent_read | state_changing | unknown

exchange(id, run_id, surface_id, action_id, identity, identity_generation, via,
         outcome, sent_us, recv_us, method, url, resolved_ip, status,
         req_blob, resp_blob, resp_len, body_shed, scope_version_id, seq)
         -- outcome: ok | timeout | conn_refused | dns_error | tls_error
         --        | scope_denied | rate_limited | bridge_lost | truncated
         --        | status_unreadable        (amended 2026-08-23)
         -- a transport failure has no HTTP status; without `outcome` a check
         -- reads silence as "not vulnerable"
         -- `status_unreadable` means the exchange COMPLETED but its final
         -- status could not be read -- the transport reported an interim
         -- (1xx) head OTHER THAN 101 and no final status line could be found
         -- behind it.
         -- (Widened 2026-08-23: the cause is not only "more interim heads
         -- than the scan tolerates". It is equally a response TRUNCATED after
         -- the interim head, which is what a CDN's `103 Early Hints` in front
         -- of a dead origin looks like, and it is the commoner shape of the
         -- two. Naming only the head count left that ending reporting the
         -- 1xx as final: measured, 30 such exchanges recorded `status=103,
         -- outcome=ok` and the §4 auto-halt never fired.)
         -- (Narrowed 2026-08-24: `101 Switching Protocols` is NOT an interim
         -- head and is excluded. RFC 9110 §15.2.2 -- the empty line ending a
         -- 101 head ends HTTP on that connection, and no further status line
         -- ever follows -- so "a 1xx head with nothing behind it" is what a
         -- CORRECT, SUCCESSFUL upgrade looks like, not a truncation. It is
         -- recorded `status = 101, outcome = ok`. The widening above without
         -- this exclusion was measured to fire the §4 auto-halt after ten
         -- SUCCESSFUL WebSocket upgrades against a healthy host, filing all
         -- ten as `status = 599, outcome = status_unreadable`: the same rail
         -- as the widening, in the opposite direction. 100 and 102 head-only
         -- remain genuine truncations and remain unreadable.)
         -- `status` then holds
         -- the conservative sentinel 599 so §4's auto-halt counts it as an
         -- error rather than a healthy sample, and this outcome is the only
         -- thing distinguishing that sentinel from a peer that genuinely
         -- answered 599. Without it, an exchange whose own captured body
         -- reads `HTTP/1.1 200 OK` is indexed as a 5xx with nothing to say
         -- otherwise. This is a §5 vocabulary value AND a §6 wire value, and
         -- they are deliberately the same string: a mapping layer between two
         -- vocabularies that differ by one entry is how they drift.

-- The table that makes a report honest. Records that a check RAN.
check_run(id, run_id, surface_id, insertion_name, check_id, check_version,
          started_us, ended_us, verdict, reason, requests_sent)
          -- verdict: pending | clean | finding | inconclusive | skipped | error
          -- reason:  scope_denied | transport_error | auth_expired | rate_limited
          --        | budget_exhausted | blocked_by_edge | profile_disabled
          -- a 'pending' row is written BEFORE the check runs, so a crash leaves
          -- evidence that the surface was never reached

finding(id, engagement_id, dedupe_key, issue_type_id, title, description, impact,
        remediation, cwe, references, severity, severity_source, confidence,
        created_by, status, surface_id NULL, insertion_name NULL, insertion_kind NULL,
        host, scope_level, payload, normaliser_version, first_seen_run, last_seen_run,
        UNIQUE(engagement_id, dedupe_key))
        -- scope_level: engagement | host | surface | insertion
        -- surface_id/insertion_name NULLABLE: TLS and cookie-flag findings have no
        -- insertion point; a shared error handler has many surfaces

finding_observation(finding_id, run_id, observed, exchange_id, severity_at,
                    confidence_at, ts_us, PRIMARY KEY(finding_id, run_id))
        -- presence per run as a SET, not a range. Found in run 3, fixed in run 5,
        -- reintroduced in run 7 must be expressible — that is the retest deliverable.

finding_status_event(id, finding_id, from_status, to_status, actor, note, ts_us)
        -- append-only; finding.status is a cached projection.
        -- A TRIGGER rejects any row where actor='agent' AND to_status='confirmed'.
        -- The rule is enforced by the database, not by discipline.

evidence(id, finding_id, seq, role, kind, exchange_id NULL, ref, note, captured_us)
        -- immutable

agent_action(id, engagement_id, run_id, ts_us, actor, tool, args_blob,
             result_summary, why)

denial(id, run_id, ts_us, kind, method, url, resolved_ip, reason, scope_version_id)
        -- kind: scope | method | dangerous | rate | budget | not_configured

quarantine(id, received_us, engagement_id_claimed, method, url, reason, raw_blob)
        -- inbound traffic that did not match this engagement (wrong engagement_id on
        -- hello, or a proxy observation matching no scope rule). Never silently
        -- discarded, never allowed into `exchange`.
```

**Insertion points are derived, not stored.** There is no `insertion` table in v1:
`surface.detail` parses them from the exemplar exchange on demand, and
`insertion_name` / `insertion_kind` are carried as columns on `check_run` and `finding`
where they are needed for identity. If parsing proves expensive at scale, materialising
them is an additive change.

**`dedupe_key` is one canonical NOT NULL TEXT column:**

```
type|scheme|host|port|method|path_template|insertion_kind|insertion_name
```

Literal `-` for absent parts, never `NULL` — SQLite treats NULLs as distinct in a UNIQUE
index, which would silently defeat the constraint. Method and insertion kind are included
because `GET /api/order/{n}` leaking another tenant's data and `POST /api/order/{n}`
accepting mass-assignment are different findings.

**Blobs.** Content-addressed within the engagement: `blobs/ab/cd/<sha256>`. Written
`tmp/<uuid>` → fsync → verify digest → atomic rename. Length stored alongside the hash and
verified on read; a torn write must fail loudly rather than poison every future identical
body. Per-engagement partitioning is deliberate: cross-engagement dedupe saves little and
makes contractual data destruction (`rm -rf engagements/<id>`) impossible to do correctly.

## 6. Bridge protocol

Unix domain socket. Not a TCP port — this capability can send arbitrary HTTP into a
client's production estate, and a loopback port is reachable by any local process or
browser tab.

```
$XDG_RUNTIME_DIR/hx/<engagement-id>.sock     dir mode 0700, socket 0600
```

Never hardcode uid 1000. Fresh random basename per run; unlink on shutdown; refuse to start
if the path exists. On `accept`, verify `SO_PEERCRED` — the socket authenticates a UID, not
a program, so peer credentials are checked and the connecting pid's executable is logged.

**Python listens; Burp dials in.** The harness holds state and outlives Burp. A Burp
restart is a reconnect, not an outage.

**Framing:** `[4-byte BE length][JSON header][raw body bytes]`. Control in JSON, payload in
bytes, no base64 tax on a 1.2 MB body.

**Every header carries a monotonic `id` and an absolute `deadline`.**

| Direction | Frame | Notes |
|---|---|---|
| burp → py | `hello` | `{protocol, ext_version, pid, burp_version, instance_id, engagement_id}` |
| py → burp | `configure` | scope + `scope_sha256` + identities + limits + profile + `engagement_id`; returns `config_epoch` |
| py → burp | `send` | carries `identity_id` **per request** — there is no global active identity |
| burp → py | `result` | `{id, config_epoch, status, bytes, ms, outcome}`. **Amended 2026-08-23:** not `exchange_id` — the extension has no store row id, so the Python side assigns one on persist; `config_epoch` is carried instead so a result can be attributed to the authorisation it was decided under. `outcome` is load-bearing on this frame, not decoration — it carries `status_unreadable`, the only thing separating the 599 sentinel from a peer that genuinely answered 599 (see §5). `status` is the **final** status, not the transport's: a peer may put `1xx` heads in front of it (measured against Burp Community 2026.7.3 — `toByteArray()` carries both heads and `statusCode()` answers `103`), and reporting the interim one would feed a healthy sample to the §4 auto-halt. **Amended 2026-08-24: `101 Switching Protocols` is the exception and is reported as itself.** It is not an interim head — RFC 9110 §15.2.2 ends HTTP on that connection at the 101's empty line, so nothing follows it — and treating it as one reports `599 / status_unreadable` for a successful upgrade and auto-halts the run after ten of them |
| burp → py | `error` | `{id, class, detail}`, plus `retry_after_us` on `rate_limited`; class ∈ `scope_denied, method_denied, dangerous_denied, rate_limited, budget_exhausted, not_configured, unmanaged_credential, transport_error, timeout, bridge_lost`, **and (amended 2026-08-23) `bad_frame`, `engagement_mismatch`, `bad_config`, `protocol_mismatch`** — the four that refuse a frame the extension cannot safely act on. `bad_frame` and `engagement_mismatch` refuse one frame and keep the channel; `bad_config` and `protocol_mismatch` drop to DENY-ALL first. **Also amended 2026-08-23: `halted` and `unknown_frame`.** Both were already on the wire and in neither list — `halted` is what §4's three kill paths answer a `send` with and this section's own auto-halt row assumes it exists, and `unknown_frame` refuses a frame type this version does not know (one frame, channel kept, like `bad_frame`). An emitted class missing from this list is a silent denial: the store's routing tables are checked against THIS enumeration, so a class that is not here has nowhere to go and `hx.store.records` will not have been asked where it belongs. The class list is now derived from the emit sites by a test rather than transcribed, because it had drifted twice |
| burp → py | `exchange` | unsolicited proxy observation, no `id`. **Amended 2026-08-24:** carries TWO bodies, the redacted request and the redacted response, because a proxy exchange is only evidence if both halves are kept. `result` carries one body and that asymmetry is deliberate — on the send path the harness already holds the request it asked to be sent, and on this path nobody does |
| burp → py | `halted` | unsolicited, no `id`: `{reason, host, window}`. Auto-halt is extension-initiated, so there is no outstanding `id` to answer. Without this frame an auto-halt is invisible until the next `send` fails, and `run.status = aborted` has no `stop_reason` to record |
| py → burp | `halt` / `resume` | takes effect at next issuance |

`rate_limited` carries `retry_after_us`. The distinction is load-bearing for the agent:
`rate_limited` means slow down and retry, the three `*_denied` classes mean the answer will
not change, and `budget_exhausted` means this run is over. **Nothing retries
automatically** — see the in-flight rule below.

`unmanaged_credential` is returned for a `send` carrying an `Authorization`, `Cookie` or
`Proxy-Authorization` header the extension did not inject. The request is refused and never
persisted. See §7.

**Engagement mismatch is fatal.** The harness refuses a `hello` whose `engagement_id`
differs from the open engagement; every `send` carries it and the extension refuses a
mismatch. Unmatched inbound traffic goes to a quarantine table, never into `exchange`.

**In-flight calls on disconnect.** Every outstanding `send` fails with `bridge_lost` —
distinct from `timeout` and `conn_refused`. **Never auto-retry across a reconnect**: a
replayed state-changing request is worse than a failed one. Retry is a decision the caller
makes explicitly.

**Backpressure has two classes.** *Solicited* exchanges (anything issued via `send`) are
**never shed** — they are about to become evidence; if the queue is full, that one caller
blocks. *Unsolicited* proxy observations may shed, and shed **bodies first**: the skeleton
row (seq, ts, method, url, status, length) is always persisted with `body_shed = 1`. A
coverage number computed over rows that were silently discarded is a lie.

## 7. Identity and authentication

`hx` works against authenticated applications in the same sense Burp does, and identity
sits **below** the check layer: a check never knows about authentication.

**Identity travels per-request in the send frame header.** There is no global mutable
active identity — two concurrent flows would otherwise issue under one identity and record
another. The extension holds `identity_id → {headers, cookies, origins, generation}` and
applies it immediately before issuance.

**v1 does not use `registerSessionHandlingAction`.** The probe proved it *registers* on
Community; registration is not invocation, and v1 should not depend on unverified
behaviour. Identity is applied on the send path we control. Revisit once invocation is
measured.

**v1 identity strategies:** `static` (client-supplied cookie/bearer) and `programmatic`
(a command or request sequence that prints credentials). For SSO/MFA applications you log
in by hand once in Burp's bundled Chromium and hand the session to `hx` — which is what a
consultant does anyway, and it beats automating an Okta push prompt.

**Identity has a generation and a liveness proof.** After any refresh, a per-identity
canary request must return the expected authenticated signature before the queue is
released; on failure the run halts rather than continuing. `exchange` records
`identity_generation` and whether the identity was `proven` or `assumed`. Without this, an
SSO session dying at 01:50 produces six hours of unauthenticated traffic that every check
reads as "not vulnerable".

**Credentials are redacted inside the JVM, before hashing.** The extension knows exactly
which byte ranges it injected and replaces them with a stable placeholder
(`{{identity:<id>:authz}}`) in the copy that crosses the bridge. Payload and request
structure stay verbatim, so evidence remains defensible; a live production session cookie
is never written to disk. **This is the one item that cannot be retrofitted** — once raw
credentials are content-addressed into the blob store, they are in every backup. Redaction
therefore runs **before** hashing: the blob store is content-addressed, so hashing raw bytes
and redacting afterwards means the raw bytes are already on disk.

**Responses need it too, and injection cannot key them.** A response's `Set-Cookie` is a
live production session cookie the extension never injected, so the rule above does not
reach it — as originally written this spec redacted the credential we supplied and stored
the one the application handed back. Response `Set-Cookie` **values** are replaced with
`{{observed:set-cookie}}` before hashing; the cookie name and its attributes stay, so
session-fixation and cookie-flag checks still work. This is header-name matching, which is
too weak to be the *primary* mechanism for requests — there, injected byte ranges are known
exactly — but for responses there is nothing to key on, so it is that or store them.

**Until identity injection exists, the send path fails closed.** The redaction machinery
and the placeholder format ship with the send path, with nothing yet registering ranges. A
`send` carrying a credential header the extension did not inject is refused with
`unmanaged_credential` and never persisted, so no raw credential can reach the blob store
in the window before §7 is implemented.

**Multi-identity replay** is a first-class primitive: the same request under
`admin | user_b | anon`, responses diffed. Broken access control is the highest-yield
finding class on real engagements, and it needs two valid sessions and a semantic
comparison rather than a payload.

## 8. Tool layer

One definition; an MCP adapter in v1 and an embedded loop later. **All v1 tools are
synchronous** — no job runner, no job table, no polling.

**Principle 1 — handles and digests, never payloads.** But a bare
`{exchange_id, status, bytes, ms}` is uninformative: twelve XSS payload variants against
one endpoint return twelve identical-looking tuples. So `send` returns a *digest*:

```json
{"exchange_id":"x-8841","status":200,"bytes":1208207,"ms":340,
 "content_type":"text/html","body_sha256":"…","first_line":"HTTP/1.1 200 OK",
 "delta_vs_baseline":{"status_changed":false,"len_delta":+37,"new_tokens":["hZq9x"]}}
```

**Principle 2 — reading is match-addressed, not offset-addressed.** An agent does not know
where in a 1.2 MB bundle the interesting bytes are. `http.grep` is the documented default;
`http.body(range)` is the escape hatch used after a match yields an offset.

**Principle 3 — every list tool returns a uniform envelope:**
`{rows, returned, total, truncated, next_cursor, facets}`, default limit 50, stable
ordering by novelty/risk. A tool that can return 3,400 rows must never do so by default.

**Principle 4 — tri-state outcomes everywhere.** "Check found nothing" and "check could not
run" must be distinguishable at every layer, or a dead session renders as a clean report.

**Principle 5 — state-changing tools require `why`**, written to `agent_action`. The agent
never handles secrets: identity is passed by *name*, resolved below the tool layer, so
`args_blob` can be stored verbatim.

**Principle 6 — the safety profile is enforced in the extension**, and the tool layer
merely reports what was refused. The agent cannot self-escalate.

### v1 tools (17)

```
run.start(kind, why)              run.finish(status, note)
run.journal(since|last_n, tool)   ← what have I already tried this run
run.resume()                      ← purpose-built recovery brief after compaction

surface.query(filter, cursor)     surface.detail(surface_id)

http.send(request, identity, why) → digest
http.grep(exchange_ids, pattern, part, context_bytes)
http.body(exchange_id, part, range)
http.replay_as(exchange_id, identities[]) → per-identity digest + diff

crawl.run(target, identity, max_pages, max_seconds) → surface delta  [synchronous, bounded]

checks.list(class)
scan.run(surface_ids[], checks[], budget) → check_run outcomes   [synchronous, bounded]

finding.record(...)               finding.query(filter, cursor)
evidence.attach(finding_id, exchange_id, role, note)
report.render(engagement) → Markdown
```

`run.journal` and `run.resume` exist because a long run compacts. Without them the agent
re-scans surfaces it already covered and cannot tell what it has done. This is the
loop-prevention hole and the compaction-recovery hole, and they are the same hole.

**Not agent-facing:** `engagement.create`, `surface.add`, `finding.set_status`. Creating an
engagement and confirming a finding are human acts; they live in the CLI and the web app.

## 9. Discovery and crawling

Attack surface arrives three ways, all of which land in `surface` via the proxy:

1. **You browse the target** through Burp. This is the highest-quality source and it is
   how SSO/MFA applications get covered.
2. **`hx crawl`** — a CLI step driving Burp's own bundled Chromium through Burp's own
   proxy. Long crawls belong here, outside the agent session.
3. **`crawl.run`** — the same crawler as a *bounded synchronous* tool, so the agent can
   sweep a newly-discovered area mid-session. Hard budget: `max_pages`, `max_seconds`,
   `max_requests`. There is no job runner and no job table; a crawl that needs longer than
   its budget returns what it found and says it was truncated.

Measured on an Angular SPA: a link-following crawl found 7 references, all static assets;
the browser-driven crawl found 65 requests and 9 parameterised endpoints, including the one
carrying an injection flaw. Nothing reachable only through JavaScript is discoverable
without this.

**The crawler is generic, not per-application.** It follows links, walks SPA routes,
expands in-page navigation, and submits forms under the policy below. Per-engagement
*hints* (a login route, a seed URL list, selectors to click, regions to avoid) live in
`config.yaml`. Hints are optional; a hand-written script per client is not the model,
because that is the brittleness that makes scripted crawling rot.

**Form submission policy — the crawler is an egress path and is governed like one.**

- Forms are submitted with benign, identifiable values (a per-run canary token) so crawl
  traffic is distinguishable from real user data in the client's logs.
- `GET` forms are submitted freely. **Non-idempotent forms are submitted only when
  `active_mutate` is enabled**, and never when the action matches the dangerous-path
  denylist. A crawler that finds "Delete account" and dutifully clicks it is the worst
  possible failure of this system.
- File upload inputs are skipped in v1.

**Authenticated crawling** uses a named identity, and the identity is attached only to
in-scope destinations — the same rule as every other egress. If the session dies mid-crawl,
the crawl halts rather than continuing to walk an unauthenticated app and recording it as
covered.

Crawl-discovered surfaces are recorded with `discovered_by = 'crawl'`, so coverage
reporting can distinguish what a human explored from what a machine walked.

### Path template normalisation

`surface` identity is the template, so normalisation decides how attack surface is
partitioned. Rules are applied in order and stamped with `normaliser_version`; a rule
change is therefore detectable rather than silently re-partitioning history.

| Order | Segment matches | Becomes |
|---|---|---|
| 1 | `config.preserve` patterns (e.g. `v1`, `v2`, `api`) | unchanged |
| 2 | UUID, 8-4-4-4-12 hex, any case | `{uuid}` |
| 3 | all digits | `{n}` |
| 4 | date-like: `YYYY`, `YYYY-MM-DD`, or `/YYYY/MM/DD/` runs | `{date}` |
| 5 | hex or base64-ish, length ≥ 16 | `{hash}` |
| 6 | ≥ `N` distinct values observed at this position across the engagement | `{var}` |

Rule 1 exists because version segments look exactly like slugs, and collapsing
`/api/v1/orders` and `/api/v2/orders` into one surface would hide a whole API version.

Rule 6 is the slug answer, and it is deliberately **frequency-based rather than
pattern-based**. Slugs (`/blog/how-to-reset-your-password`) are indistinguishable from
meaningful path segments by regex; they are distinguishable by *variety*. Default `N = 12`,
tunable per engagement. The cost is that the first few observations of a slug position
create separate surfaces which later collapse — so re-normalisation runs at run end and
`surface.exemplar_exchange_id` is preserved across a merge.

## 10. Checks

A check is a Python object with metadata (`id`, `version`, `class`, applicable insertion
kinds) and one method. Adding a check does **not** add a tool. This is the extensibility
surface, and it is deliberately the cheapest thing in the system to change.

```
passive          analysis only, zero extra requests          always on
active_safe      idempotent GET/HEAD payloads, bounded       on by default
active_timing    sleep payloads, capped concurrency + wall   on by default
active_mutate    non-idempotent, state-changing              OFF, opt-in per engagement
active_dos       resource exhaustion                         OFF, opt-in + confirmation
```

Every check returns a tri-state verdict and writes a `check_run` row. A check that cannot
run returns `inconclusive(reason)` — never `clean`.

**v1 check corpus** targets the reachable, high-value subset. Burp's own
`BuiltInConfigs` decompose its critical checks into detection techniques, and **18 of 24
(75%) require no Pro feature**; with an OAST collector that reaches 24 of 24. The
realistic build target is the **42 HIGH-severity non-DOM issue types**, not all 183.

v1 ships: reflected input/XSS, SQL error, boolean-differential (via
`createResponseVariationsAnalyzer`), time-based blind injection, path traversal, open
redirect, CORS misconfiguration, cookie flags, security headers, secret-in-response,
stack-trace disclosure, and multi-identity access-control diffing.

Issue text, severity and CWE mappings come from Burp's 183 vendored issue definitions, so
reports use the same vocabulary a Pro user's do.

## 11. Web app

FastAPI + Jinja + htmx. No build step, no SPA, no `node_modules` — a tool holding client
engagement data should not pull hundreds of transitive packages to render a table.

**v1 binds `127.0.0.1` only.** Tailnet access is via SSH port-forward. An unauthenticated
app that can trigger scans and holds client findings does not get bound to a tailnet
address on the promise of adding auth later; when it is bound, a per-install bearer token
lands *before* the first write endpoint.

**Screens:** engagements · engagement overview (scope + hash, runs, coverage, severity
counts) · surface · findings · finding detail with evidence chain · exchange viewer · run
progress (SSE) · agent transcript.

**The exchange viewer is the one screen worth real effort** — syntax highlighting, in-body
search, hex toggle, and side-by-side diff for `replay_as`. Everything else is a competent
table.

**Control in v1 is exactly two things:** the STOP button, and finding triage
(`new → confirmed | false_positive` with a note). Triage is in v1 because it has no
substitute — you can ask the agent to start a run, but you cannot ask it to decide whether
a finding is real.

**Not in the UI:** message editing, resend, payload crafting. That is Repeater.

## 12. Reporting

`report.render(engagement)` produces **one Markdown file** in the structure already
delivered by hand, for editing — not a format × audience matrix.

It must include a **coverage/assurance section generated from `check_run`**: which checks
ran against which surfaces, with verdicts. This is what lets you answer "did you test the
password reset flow?" and what makes a retest honest. A report that cannot distinguish
"tested, clean" from "never reached" is worse than no report.

Redaction runs on export. The report cites `scope_version.sha256` and the `authorization`
record in force, so what you were permitted to touch is part of the deliverable.

## 13. v1 scope

**In:** the crawler (CLI + bounded `crawl.run`, see §9) · the 14 tables above · bridge with correlation ids, `configure`/epoch, deny-all
default, two backpressure classes · extension-side scope, method allowlist, dangerous-path
denylist, rate limit, budgets, auto-halt, redaction · static and programmatic identities
with liveness proof · 17 synchronous tools · the check corpus above · the web app screens
above · Markdown reporting with coverage.

**Out of v1, with reasons:**

| Deferred | Why it is safe to defer |
|---|---|
| OAST service (`oast.*`, public collector) | Needs a registered domain, NS delegation, DNS-01 wildcard cert and engagement-duration uptime. Capability already proven in the lab; keep `oast.py` as a localhost lab tool. **v1 ships no blind-only checks and says so in the report.** |
| Async job runner (`crawl.status`, `scan.status`, job table) | `scan.run` is synchronous over a bounded batch with a hard budget. No resumption machinery needed. |
| `registerSessionHandlingAction` | Registration verified, invocation not. Identity applies on the send path we control. |
| `run.diff` | Monitoring-phase work; semantics cannot be got right before two comparable runs exist. `surface.query(first_seen_run=…)` covers the need. |
| Browser-login identity strategy | Log in by hand once for SSO/MFA apps. |
| Tailnet binding | SSH port-forward until auth exists. |

**Monitoring (v2)** is a wrapper: `run.kind = scheduled`, plus a diff over
`finding_observation` and `surface.first_seen_run`. The schema carries it from day one, so
it is not a rewrite.

## 14. Open questions

1. **Normalisation thresholds.** The rule set is specified in §9. What is not settled is
   the default `N = 12` for frequency-based slug collapse, and whether re-normalisation at
   run end is frequent enough. Both need tuning against a real client app; `normaliser_version`
   makes a change detectable rather than silently re-partitioning history.
2. **Edge/WAF block classification.** A 403 from Cloudflare and a 403 from the app are
   different facts. v1 handles this via `check_run.reason = blocked_by_edge` plus
   auto-halt; a proper `egress`/`block_class` model is deferred.
3. **Whether `scan.run` stays synchronous** once a real engagement has a few thousand
   surfaces. Revisit with measurements, not intuition.

## 15. Provenance

Design produced 2026-08-21 through brainstorming, then reviewed adversarially by six
independent lenses (engagement workflow, schema, agent-usability, security/blast-radius,
SRE, YAGNI) which raised 136 defects, 36 critical. Sixteen were folded in before this spec
was written. Three were raised by all six lenses independently: credential redaction,
`dedupe_key` insufficiency, and scope versioning.

Two defects were bugs introduced by composing individually-correct sections: identity
attachment to out-of-scope hosts (session cookies leaking to third parties and to open
redirect targets), and redact-on-export leaving live credentials in the evidence store.
Both are fixed above.
